# Control Number Specification

**Status: implemented (Phase 2).** Code: `apps/control_numbers/`. This
document specifies the design and records what the implementation
actually does.

## What a control number is

A control number is the persistent reference a customer uses to pay a
bill or a customer account through a payment channel. It must be:

- Globally unique within its required scope (see "Scope" below).
- Collision-resistant and securely generated — not a predictable
  sequence.
- Persistent — the same control number is reused across multiple payments
  against the same bill/account (partial payments, recurring billing).
- Free of embedded PII: no phone numbers, names, national IDs, or other
  personal data encoded in the number itself.
- Auditable: every creation is a recorded event (see
  [../apps/audit](../apps/audit)), and every retrieval of an existing
  number is distinguishable from a creation in the audit trail and in the
  [revenue engine](PRICING_MODEL.md).

## Two modes

1. **One-time bill control numbers** — issued for a single bill, expire
   or become unusable once that bill is fully paid/expired/cancelled.
2. **Persistent account control numbers** — issued once for a
   `CustomerAccount` and reused across many bills/payment cycles (e.g. a
   recurring termly fee, a monthly rent account).

## The idempotency rule (this is the whole point)

Requesting a control number for a bill/account that already has one must
**return the existing control number**, not create a second one. This is
not optional — it's the mechanism the pricing model
([PRICING_MODEL.md](PRICING_MODEL.md)) depends on to avoid double-charging
the creation fee, and the mechanism ERPs depend on to safely retry a
"create bill" call without creating duplicate control numbers (build spec
section 14, idempotency).

**Implemented as:** `apps.control_numbers.services.get_or_create_for_bill`
/ `get_or_create_for_account` — never `create_control_number(...)`.
Callers never check "does one exist" themselves; the service owns that
check. The race between two concurrent requests for the same new
bill/account is closed at the database level, not just in application
code: `ControlNumber.bill` is a `OneToOneField` (a bill can have at most
one control number, full stop, enforced by Postgres) and
`ControlNumber.customer_account` has a conditional
`UniqueConstraint(condition=Q(status="active"))` (at most one *active*
control number per account, while still allowing historical
expired/cancelled ones to exist for the same account). Both service
functions catch the resulting `IntegrityError` from a losing concurrent
request and re-fetch/return the winner's row rather than erroring —
see [../ARCHITECTURE_DECISIONS.md](../ARCHITECTURE_DECISIONS.md) ADR-010.

Every call also records an audit event —
`control_number.created` on genuine creation, `control_number.reused` on
retrieval of an existing one — via `apps.audit.services.record_audit_event`.
This distinction is what Phase 4's revenue engine will key its fee logic
off of; it is already correct and tested independently of any fee logic
existing yet (see `apps/control_numbers/tests/tests.py`).

## Format

`YYMMDD` + 6 random digits (e.g. `260812314338`), generated by
`apps.control_numbers.services.generate_value()`. Global uniqueness
(`ControlNumber.value` is `unique=True` across the whole platform, not
just per-tenant) is enforced at the database level; generation retries up
to 5 times on the astronomically unlikely event of a collision. Contains
no personal data by construction — tested explicitly
(`test_control_number_never_embeds_personal_data`).

## Lifecycle events implemented

Creation, retrieval-of-existing (no fee — see
[PRICING_MODEL.md](PRICING_MODEL.md)), cancellation
(`apps.control_numbers.services.cancel`). **Not yet implemented:**
scheduled expiry sweeping — `expire_overdue()` exists and correctly marks
overdue `ACTIVE` control numbers as `EXPIRED`, but nothing calls it on a
schedule yet; it's intended to become a Celery beat task once Phase 3
gives the platform an actual reason to run scheduled jobs (right now
nothing else does either). Reversal is a payment-domain concept (Phase 3)
and doesn't apply to a control number directly.

Balance is not tracked on the control number at all in Phase 2 — there is
no `Payment` model yet. Once Phase 3/4 add it, balance will be computed
from ledger records, never manually edited, per the same pattern already
established for `Bill.total_amount` (computed via
`Bill.recalculate_total()` from `BillItem` rows, never hand-set).
